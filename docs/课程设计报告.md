## 摘要

Scratch 采用积木式编程，作品中包含的事件、循环、条件、自定义积木、变量和列表等结构可为学习者理解计算思维提供线索。本设计实现了一个接收 Scratch 3 sb3 文件的程序分析网站，利用 ZIP 读取与 JSON 解析得到项目积木图，采用静态规则计算七个计算思维维度的参考分数，并提取角色、脚本、积木、变量等量化指标。系统提供评分证据、改进建议、JSON 导出和基于 SQLite 的分析历史。后端采用 Node.js、Express，前端采用 HTML、CSS 与 JavaScript。测试覆盖评分边界、压缩包错误、HTTP 功能链路及数据库持久化。具体评分规则是参考 Dr. Scratch 七维模型的课程实现，不代表官方算法，也不直接证明程序运行正确性或学习者能力。

关键词：Scratch；计算思维；静态分析；JavaScript；SQLite

## 1 需求分析

### 1.1 课题背景

任务书要求建立可上传 sb3 文件并提取量化指标的分析网站，指标包括但不限于 Dr. Scratch 的量化维度。图形化编程降低了语法门槛，但学习者仍需要反馈以理解程序结构、并行事件、数据操作和分解复用。本系统以可解释的结构指标为中心，帮助使用者发现作品中的特征并提出进一步检查方向。

### 1.2 功能需求

用户应能够选择或拖入 sb3 文件，得到七维评分、基础统计、角色明细、规则命中证据和改进建议。系统应支持示例分析、查看最近分析、恢复历史报告、删除记录与导出 JSON。上传错误应给出明确提示，不保存失败结果。

### 1.3 非功能需求

系统不执行上传程序，不解压项目资源到磁盘，限制上传大小及项目 JSON 大小。前端使用安全文本接口展示用户可控内容，后端 SQL 使用参数绑定。系统需在单机环境快速启动，并通过自动化测试检查核心规则。系统当前不面向多用户公网服务，暂无用户鉴权和账号级数据隔离。

### 1.4 验收边界

本次实现以 sb3 静态结构分析为范围，不运行 Scratch VM、不评分程序功能是否正确，不支持 sb2，也不声称与官方 Dr. Scratch 得分完全一致。参考资料中的 ANTLR 并非必须依赖；本设计直接使用 sb3 中已有的 JSON 结构。

## 2 总体设计

### 2.1 系统架构

采用浏览器—HTTP 服务—分析模块—SQLite 的分层结构。浏览器通过 multipart/form-data 上传；Express 接收文件并交由 ZIP 模块读取 project.json；分析模块生成报告；数据库保存摘要与完整 JSON；浏览器渲染返回结果。

输入路径：浏览器 → 上传接口 → ZIP 校验 → 项目结构校验 → 积木分析 → SQLite 保存 → 报告页面。

历史路径：浏览器 → 历史接口 → SQLite 查询 → JSON 报告 → 页面恢复。

### 2.2 模块划分

archive.js：受限 ZIP 读取、重复 project.json 和 JSON 格式校验。

analyzer.js：有效积木筛选、图遍历、七维评分、统计、重复提示和建议。

server.js：HTTP 路由、上传限制、数据库初始化与报告持久化。

public/app.js：上传与拖拽、报告展示、历史操作、示例分析与 JSON 导出。

### 2.3 技术选择

JavaScript 满足任务书所列语言范围，前后端共享语言降低实现复杂度。Node.js 内置 SQLite 提供无需额外数据库服务的持久化能力。Express 组织 HTTP 接口，Multer 处理上传，Yauzl 对 ZIP 条目进行流式读取。前端不依赖外部 CDN，便于离线展示已安装系统。

## 3 数据库设计

### 3.1 逻辑模型

分析记录是核心实体，包含唯一编号、文件名、分析时间、总分与报告。当前系统不持久化上传文件和 Scratch 资源，因此没有文件资源表或用户表。历史最多返回最近 100 条记录。

### 3.2 表结构

表名：analyses。

id：INTEGER，主键，自增，用于定位分析记录。

filename：TEXT，非空，保存清理后的文件名，最多 200 个字符。

created_at：TEXT，非空，保存 ISO 8601 UTC 时间；界面按浏览器当地时间显示。

score：INTEGER，非空，保存七维总分。

report：TEXT，非空，保存带规则版本的 JSON 分析报告。

采用单次 INSERT 保存完整分析结果，不依赖多个步骤更新同一记录。数据库启用 WAL 模式。由于记录结构为展示型不可变结果，JSON 文本避免将变化的证据数组拆分成大量关系表；如未来需要跨报告维度统计，可增加规范化的维度表和指标表。

### 3.3 数据安全与隐私

所有查询使用参数化 SQL。原始上传文件仅在内存解析，不保留到磁盘。文件名与报告仍可能包含个人信息，用户可以删除历史。当前版本访问同一实例的用户共享历史，应在可信环境使用。

## 4 核心算法设计

### 4.1 sb3 文件解析

sb3 是 ZIP 格式。程序依次读取条目，只读取根目录的 project.json，不加载 SVG、音频或其他素材。上传限制 20 MB，JSON 解压大小限制 8 MB，条目数量限制 10000。重复 JSON 条目、缺失 JSON、无效 ZIP、加密项目与错误 JSON 均被拒绝。

### 4.2 积木图与遍历

每个目标的 blocks 使用积木 ID 索引，next 指向后续积木，inputs 可引用子积木，parent 用于层级回溯。统计排除影子菜单积木和数组形式的内联变量记录。自定义积木参数分析另读取影子原型。顶层无父节点积木作为脚本根，使用显式栈与 visited 集合遍历，避免循环引用导致无限循环。无法从根访问的有效积木被列入不可达统计。

### 4.3 七维评分

七个维度分别为抽象与问题分解、并行性、逻辑思维、同步性、流程控制、用户交互和数据表示。每维取命中的最高等级（0–3 分），总计 21 分。抽象维度从多个脚本到自定义积木与参数；并行性统计同事件脚本数量和跨角色分布；逻辑分析条件、逻辑运算及嵌套；同步分析等待与广播；流程控制分析顺序连接、循环和嵌套；交互识别绿旗、按键、鼠标和视频/音量输入；数据表示识别角色属性、变量和列表。

具体规则见随附 scoring.md 及源文件 analyzer.js。每个维度包含等级规则、命中布尔值与最多八个相关积木证据，便于用户复核。

### 4.4 代码质量提示

空事件脚本通过事件帽子是否有 next 判断。疑似重复脚本对三块及以上主链生成序列签名，保留 opcode、字段和输入模板，嵌套引用使用占位标记。该方法可能误报，不用于抄袭判定。损坏的 next/parent 引用最多保存 100 条提示。

### 4.5 复杂度与改进空间

基础统计和可达遍历在积木与边数量的线性范围内。嵌套检查逐节点沿 parent 链回溯、重复检测逐脚本扫描主链，在极端共享链或深层结构下可能退化到二次量级。当前通过上传和积木数量限制控制资源，但同步分析仍会阻塞单个 Node.js 事件循环。公开部署可增加 worker_threads、耗时上限、父链深度限制以及子树签名缓存。

## 5 系统实现与界面

### 5.1 上传流程

前端执行扩展名与大小检查，构建 FormData 发送 file 字段。后端重复执行大小与结构限制，不依赖前端检查。分析成功后写入数据库，再返回带 id、文件名和时间的完整报告。失败请求返回 JSON error；成功记录不会由非法上传创建。

### 5.2 报告展示

总分卡片和进度条展示七维结构画像，指标卡片展示角色、积木、脚本、变量、列表和质量数量。角色表提供舞台与角色明细，折叠区域提供规则与积木证据。页面使用 textContent 展示文件名与角色名，避免将项目数据作为 HTML 插入。

实际界面截图：docs/screenshots/home.png、docs/screenshots/report.png；移动端截图：docs/screenshots/mobile.png。Word 版本请按教师要求插入这些截图。

### 5.3 历史与导出

GET /api/history 返回最近记录摘要，GET /api/history/:id 返回完整报告，DELETE 删除指定记录。JSON 导出在浏览器端从当前报告生成 Blob，不需要重新分析。

## 7 问题分析与讨论

影子积木属于项目格式的辅助结构，若直接统计全部 blocks 会夸大积木数；但自定义积木原型可能是 shadow，若完全忽略会漏掉参数。本设计分离有效积木统计与原型检查。

损坏项目可能含循环引用。遍历与父链回溯采用访问集合避免死循环；并限制输入规模。深层回溯仍有性能改进空间。

压缩包体积小并不代表 JSON 解压体积小，因此除上传大小外还检查条目声明大小与实际读取长度。

评分规则具有近似性。例如相同事件不保证运行时同时执行，重复主链不代表完整语义相同。报告明确显示规则和局限，避免给出无法验证的能力判断。
